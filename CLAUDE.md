# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Godot 4.7 C++ GDExtension (`opencv_aruco`) that statically links OpenCV (via Conan) to detect ArUco markers and compute their 6DoF poses. The main deployment target is a Meta Quest 3 (Android arm64, OpenXR passthrough AR); Windows desktop is the development platform.

The repo is split in two, and the split is the thing to hold on to:

- **`project/addons/opencv_aruco/`** — the DISTRIBUTABLE addon, and the product. Its `ArucoMarkerTracking` node publishes every detected marker as a genuine `OpenXRMarkerTracker` on the `XRServer`, so it is a drop-in for the OpenXR spatial-entity marker route that the Quest runtime only serves for QR codes. It has no scene-tree dependencies and no dependency on anything else in `project/`. `build_addon.yml` packs it, `GodotAndroidCamera` and `CameraServerExtension` into one release zip.
- **`project/` (everything else)** — the demo that consumes it, plus the MEASUREMENT APPARATUS (`detection_diagnostics.gd`, `tcp_debug_stream.gd`, `tools/`) that every calibration number in `src/OpenCVProcessor.h` came out of. Deliberately **not shipped**: it attaches to the addon through three signals, and the dependency runs one way only, so the addon parses and runs without any of it.

When changing something, the first question is which half it belongs in. Anything a consumer needs goes in the addon; anything that exists to measure or prove something stays outside it.

## Build commands

There is no test suite or linter. Verification = build the extension, run the Godot project (desktop) or export + sideload the APK (Quest).

```powershell
# Windows native (DLL -> project/addons/opencv_aruco/bin/windows/)
scons                                   # defaults to platform=windows target=template_debug

# Android arm64 for Quest 3 (.so -> project/addons/opencv_aruco/bin/android/)
$env:CONAN_HOME = "C:\c"                # space-free Conan cache — REQUIRED on this machine
$env:ANDROID_HOME = "C:\asdk"           # junction to the real Android SDK — REQUIRED on this machine
scons platform=android arch=arm64 target=template_debug
```

- This machine's user path contains a space (`C:\Users\Paul Geiger`), which breaks Autotools deps and godot-cpp archiving — hence the two env vars above (README section 5b.4). Keep `ANDROID_HOME` consistent between builds; switching between junction and real path forces a full rebuild.
- First build compiles OpenCV from source through Conan (~10–20 min); later builds hit the Conan cache. Per-target Conan output lives in `conan_install/<platform>.<arch>.<target>/`; delete that folder or touch `conanfile.py` to force a dependency re-resolve.
- `SConstruct` bootstraps Conan itself (pip install + `conan profile detect`) — no manual Conan setup needed. For Android it uses the checked-in Jinja profile `profiles/android-arm64` (NDK path derived from `ANDROID_HOME`); `CONAN_HOST_PROFILE` overrides it.
- APK export happens in the Godot editor on Windows (Project > Export, preset "Meta Quest 3"). The editor does NOT build the Android `.so` — it must already exist in `project/addons/opencv_aruco/bin/android/` before exporting. Sideload: `adb install -r <path>.apk`; stop the app: `adb shell am force-stop de.unigreifswald.opencvaruco`.

## Naming invariant

The library name `opencv_aruco` and entry symbol `opencv_aruco_library_init` must stay consistent across three places: `SConstruct` (`libname` and `bindir`), `project/addons/opencv_aruco/bin/opencv_aruco.gdextension`, and `src/register_types.cpp`. godot-cpp composes filenames as `<lib?><name>.<platform>.<target>[.double].<arch><suffix>` — note `.double` comes BEFORE the arch, and Windows DLLs have no `lib` prefix while Linux/Android `.so`s do (the Android SCons branch forces `SHLIBPREFIX="lib"` because Windows hosts default to no prefix).

## Architecture

Data flows: camera frame (GodotAndroidCamera plugin on Quest, CameraServer otherwise) → GDScript worker thread → C++ OpenCV detection → camera-space marker poses → baked to **play space** with the head pose at the frame's capture time → published as `OpenXRMarkerTracker`s on the `XRServer`.

**Play space, not world space — and the C++ cannot tell the difference.** `detect_and_solve_all` computes `head_pose * lens_pose` and pre-multiplies it onto every solvePnP result, so the output is in whatever space the caller's `head_pose` was in; the words "world space" in some C++ comments are a *name*, not a claim. The GDScript hands it a play-space head pose (`XRServer`'s `"head"` tracker, or `OpenXRHeadLocator`, which returns play space natively), because that is the space an `XRPose` has to be in — `XRAnchor3D` applies world scale and the reference frame itself. World space appears in exactly one place, `get_marker_world_pose()`.

**C++ side (`src/`)** — `OpenCVProcessor` (a `Node`) exposes exactly one detection entry point, **`detect_markers(image, head_pose, corners_out)`** (two legacy ones — `get_6dof_of_all_aruco_patches_from_picture` reading a file with `cv::imread`, and `..._from_webcam` driving a `cv::VideoCapture` — were deleted in 2026-08: nothing called either, and each carried its own copy of the OpenCV→Godot change of basis, i.e. three places for a sign to be wrong in the one part of this codebase where that is hardest to notice. An offline still-image path, if ever wanted again, is `detect_and_solve_all` with an identity `head_pose`, which is the same thing the deleted picture function computed). It takes a frame the caller already owns (avoids a second capture) plus the head pose at that frame's capture time — the only per-frame input, since only the caller can know it. It runs ArucoNano's `ArucoDetector` (vendored header-only `src/aruco_nano.h`) + `solvePnP` and returns a Dictionary of marker id → `Transform3D` in **world space**: `head_pose * lens_pose` is pre-multiplied onto every result, so the caller has nothing left to apply (identity `head_pose` yields near-camera space — OpenCV→Godot basis change = 180° X-flip baked in). `corners_out` is a debug-only out-parameter (Godot Dictionaries are shared references): it receives id → the 4 detected pixel corners, divided back out of the downscaled detection frame into the original frame's pixel space, filled before the solve loop so it shows what the detector saw rather than what survived `solvePnP` — for the TCP overlay.

Everything else it needs is an **inspector property of the node** (`camera_intrinsics`, `camera_distortion`, `image_downscale_factor`, `lens_rotation_raw`, `lens_translation`, `aruco_patch_size`, `aruco_patch_sizes`, `marker_dictionary`) rather than a call argument — that is what collapsed a 7-argument call to 2, and it keeps invariants that used to span the language boundary inside one class: the intrinsics are scaled by the *clamped* downscale factor at the point the frame is resized, and the distortion `cv::Mat` is built in its setter instead of being rebuilt from a `PackedFloat64Array` every frame. The setters rebuild the derived values immediately, so an edit in the **remote inspector of a running deploy takes effect on the next frame** — notably true of the lens pose, which used to be derived once in GDScript's `_ready` and could not be tuned live at all. `get_marker_size(id)` is the single id → side-length resolution (table entry when present and positive, `aruco_patch_size` otherwise) and is bound so the GDScript scales the rendered box with the exact number `solvePnP` used; `get_lens_pose()` exposes the decoded transform for the hand-eye capture — which is why `DetectionDiagnostics` has to be a *child* of this node. Note that `Vector4`/`Quaternion`/`Vector3` components are `real_t` = float32, so the intrinsics and the lens rotation hold ~7 significant digits regardless of the inspector's step — well under the calibration's own noise, but it is why the inspector will not show every digit in the source. Every property carries an explicit `PROPERTY_HINT_RANGE` step for exactly one reason: without a hint the inspector snaps to 0.001, and editing a distortion coefficient there rounds both tangential terms to zero. On Android it also reads the Quest passthrough camera intrinsics via the NDK Camera2 API — the Quest's world-facing passthrough cameras are ids "50"/"51". That dump, and everything else that prints, lives in `dump_build_info_and_intrinsics()` (which calls the Android-only `dump_quest_camera_metadata()`; both are named for what they do — logging only, nothing the detection needs) rather than the constructor: the class is now a node **authored in the scene**, so `PackedScene` constructs it before it applies a single property and long before any `_ready`, leaving no way to set the debug-print static early enough. GDScript calls `set_debug_prints_enabled()` and then `dump_build_info_and_intrinsics()` on consecutive lines of `_ready`; the constructor is silent and builds only the detector. `dump_build_info_and_intrinsics()` is idempotent and returns immediately under `is_editor_hint()`, since opening the scene in the editor constructs the node too.

**`marker_dictionary`** selects `ARUCO_MIP_36h12` (default) or `DICT_4X4_50`, one at a time — ids collide between dictionaries and each extra one costs its own detection pass. It exists because the two branches this repo merged disagreed on it, and either choice would have invalidated a set of already PRINTED markers. Its setter is the one that does **not** rebuild its derived value: it writes an int, and the next detection notices `detector_dictionary != marker_dictionary` and rebuilds on the DETECTION thread. Rebuilding in the setter would reset the `unique_ptr` on the main thread while the worker is inside `detector->detectMarkers()` on it — a use-after-free, not a torn value.

**Thread safety of these properties** is "copy once at the top of the detection", and for two of them that is a lifetime requirement rather than a nicety. `camera_intrinsics` goes into `K_active` so four separate reads cannot mix two calibrations. `distort_mat` goes into `D_active` because it is passed **by reference** into `cv::solvePnP` while `rebuild_distortion()` reassigns the member on the main thread — a header rebind plus a refcount drop under a concurrent reader. That was latent until the addon gained `_approximate_desktop_intrinsics()`, which writes `camera_distortion` at runtime. `aruco_patch_sizes` gets the same treatment (copy-on-write pointer swap, read per marker *inside* the solve loop), which is why the id → size rule lives in a static `marker_size_from(table, fallback, id)` that both `get_marker_size()` and the loop go through.

`OpenXRHeadLocator` (also a `Node`, `src/OpenXRHeadLocator.{h,cpp}`) is the second registered class: it returns the head pose at an **arbitrary** `XrTime` via `xrLocateSpace`, which for a time in the past is the runtime's *measured* estimate rather than the prediction the pose history holds. It creates its own `XR_REFERENCE_SPACE_TYPE_VIEW` space (Godot exposes the play space but not its internal view space) and locates it against `OpenXRAPIExtension.get_play_space()`; `locate_head(xr_time)` returns `{valid, tracked, transform, flags, result}`, with `transform` in **play space** — the caller reapplies `XROrigin3D`, `XRServer.get_reference_frame()` and the world scale (`_play_space_to_world`). The `XrPosef` → `Transform3D` conversion is done **by hand** (7 floats; OpenXR and Godot share the right-handed Y-up convention) and must stay that way: `OpenXRAPIExtension.transform_from_pose()` takes a `const void *` that godot-cpp does not marshal through, and measured on device it returns **identity for every pose**, silently and with no error — which reads as a plausible-but-wrong pose sitting head-height from the real one and never changing with time. Nothing links the OpenXR loader: Godot already owns the instance and session, so the three entry points come from `get_instance_proc_addr` and `src/openxr_minimal.h` hand-declares only the structs/enums they need (vendoring the real SDK header would mean a new include path for both platforms or a cross-compiled Conan dep, for three structs). The VIEW space is a child of the XR session, so it is released on `OpenXRInterface.session_stopping` — the destructor is too late, the session is usually gone by scene teardown.

**Scene layout (`project/main_3d.tscn`, the main scene)** — root `main3d` (`Node3D`, `main_3d.gd`), with `ArucoMarkerTracking` (a plain `Node` carrying the addon script, with `TcpDebugStream` and `DetectionDiagnostics` as its children), `XROrigin3D` (carrying `xr_startup.gd`) → `XRCamera3D` → `OpenXRMetaEnvironmentDepth`, `DirectionalLight3D`, and `CameraLayer` → `CameraPreview`. The tracking node is set to `DICT_4X4_50` with marker sizes 0.10 / 0.094 / 0.10 m for ids 0–2 — the markers glued to the CPR mannequin — which `drop_in_test.gd` relies on (see its NOTE on the dictionary anchor).

The tracking node is a **sibling** of the `XROrigin3D`, not a child of it, and that is the whole point of the addon shape: it reads the head pose from `XRServer` and publishes back to `XRServer`, so it needs a path to no other node and can be dropped anywhere in a consumer's scene. `main_3d.gd` is a pure demo consumer — it spawns an `XRAnchor3D` per tracker from `XRServer.tracker_added`, filters on `tracker is OpenXRMarkerTracker` with **no name matching**, and would keep working unchanged if the engine's own marker backend published those trackers instead.

**No application lives here.** The CPR trainer sat in this project from 2026-09-16 to 2026-09-25 as a snapshot of quest-aruco-avatar's app layer, rewired onto the addon; it was removed again because a second copy of an app that is developed elsewhere only drifts. It is owned by quest-aruco-avatar (github.com/ardrabauldwin/quest-aruco-avatar), which consumes this repo's addon folders as released rather than building the extension itself.

Still true and still worth remembering: with `reloadable = false`, a node whose type comes from the DLL loses its script assignment and every exported override if **the scene is saved while the extension failed to load**. The addon node itself dodges this (plain `Node` + script), but the processor it owns is a DLL type, so never save a scene that opened with errors.

**The addon node (`project/addons/opencv_aruco/aruco_marker_tracking.gd`, `class_name ArucoMarkerTracking extends Node`)** — the whole pipeline, and the only file a consumer has to understand. It OWNS an `OpenCVProcessor` by composition (`processor = OpenCVProcessor.new()`, freed in `_exit_tree` — nothing else would, since it never enters the tree) rather than extending it. That is what keeps the node a plain scripted `Node`: a consumer's scene holds no DLL-typed node, and the addon can sit anywhere.

Per detected marker it publishes one genuine `OpenXRMarkerTracker` under `openxr/spatial_entity/aruco_<id>` — the upstream prefix, so prefix-filtering consumers match, with a DETERMINISTIC suffix the real backend cannot offer (its entity ids are runtime-assigned), which is what lets an `XRAnchor3D` be pre-authored against a known marker id. Everything is populated BEFORE `add_tracker`, so a `tracker_added` handler always sees a complete tracker. Loss is two-stage, mirroring the engine's own capability: past `marker_lost_timeout_ms` (500 ms) the pose is invalidated and the state goes `PAUSED` with the tracker KEPT, so consumers hold their last pose and `show_when_tracked` hides; past `marker_stopped_timeout_s` (10 s) the state goes `STOPPED` and the tracker is removed. Pruning happens on a fresh detection result, never on a timer — absence is only evidence once a frame that could have contained the marker has been looked at, so a stalled camera leaves trackers in place instead of evaporating on "no news". `_marker_poses`/`_marker_last_seen` deliberately outlive the tracker, because a consumer asking "how stale is my last good pose?" must still get an answer after removal.

**Calibration is written through, not duplicated.** The processor's inspector page is invisible (it is not in the tree), so the node re-exports `camera_intrinsics`, `camera_distortion`, `image_downscale_factor`, `lens_rotation_raw`, `lens_translation`, `default_marker_size`, `marker_sizes` and `marker_dictionary`, each with a setter that pushes into the native property. Setters alone are not enough and neither is one push: `PackedScene` applies exports BEFORE `_ready`, when `processor` is still null, while inspector edits arrive AFTER it — so `_push_calibration()` runs once right after `new()` and the setters carry it from there. **The export defaults are identical to the C++ defaults on purpose**, which makes that push a no-op for an untouched node; `project/tests/drop_in_test.gd` asserts exactly that. Get it wrong and the GDScript literal silently overrides a measured calibration for every consumer, with nothing anywhere reporting it — which is precisely how a ~0.9° lens-pose error survived three branches (see the CAUTION block in `OpenCVProcessor.h`).

**Two camera backends, chosen in `_ready` and never mixed.** PUSH is the `GodotAndroidCamera` plugin (CameraX): raw Y-plane bytes on the CPU, no GPU→CPU readback, plus each frame's SENSOR TIMESTAMP. PULL is `CameraServer` + `CameraTexture.get_image()`, used on desktop and on a Quest whose APK lacks the plugin; it has no timestamp, so `camera_latency_ms` (50 ms) is the only correction, and the readback is skipped entirely while a detection is in flight because it is a main-thread GPU stall that would otherwise be paid several times per detection and thrown away. Both plugins are OPTIONAL dependencies and must stay reachable without being *named*: a typed `var x: AndroidCamera` is a **parse error** in a project without that addon, which would take the whole script down. `AndroidCamera` is a GDScript global class, so `ClassDB` cannot help — it is `load()`ed by path into untyped vars. `CameraServerExtension` is native, so `ClassDB.instantiate()` does work there. The same trap is why the addon never names `DetectionDiagnostics` or `TcpDebugStream`.

Detection (~40 ms on Quest: ~20 ms `detectMarkers` since the ArucoNano swap, down from ~60 ms with OpenCV's, plus `solvePnP`) runs as one-shot `WorkerThreadPool` tasks — at most one in flight, collected by `is_task_completed` polling, with `wait_for_task_completion` doubling as the memory barrier — and a single pending-frame slot (newest frame wins). `get_image()` and every `XRServer`/tracker write stay on the main thread. Note `_poll_detection_task` is called from `_dispatch_detection` as well as `_process`, so on the PUSH path trackers can be published from the camera callback rather than during `_process`; still the main thread, since plugin signals are marshalled onto the engine loop. The `enabled` switch has to be enforced in BOTH places for the same reason: its early return lives in `_process`, which pushed frames never enter.

**Capture-time head pose.** Pairing old pixels with the live head pose bakes an error proportional to head speed, so poses are baked with the head pose at the frame's capture time. Two sources, in order of quality. `OpenXRHeadLocator.locate_head(xr_time)` asks the runtime for the pose at an arbitrary `XrTime`, which for a time in the past is its fused, MEASURED estimate — and it returns play space natively, so nothing has to be converted. On the PUSH path the frame's sensor timestamp maps to `XrTime` (identity on the Quest passthrough feed, where both clocks are CLOCK_MONOTONIC); on the PULL path there is no sensor timestamp but `pdt` IS an `XrTime`, so `pdt − camera_latency_ms` works with no clock bridge at all. Failing that, a timestamped pose history is interpolated (`_head_pose_at`), sampled once per rendered frame from `_head_pose_now()` — the raw `XRServer` `"head"` tracker, with a flat-mode fallback that strips the `XROrigin3D` transform and the reference frame off the active camera, so the history is play space either way. On the Quest each history entry is stamped with the time its pose DESCRIBES — xrWaitFrame's predicted display time — rather than with "now", because OpenXR hands out poses predicted for the upcoming display: measured on device that lead is 40–80 ms, shrinks as the render rate rises and sawtooths ~40 ms peak-to-peak within that (pdt steps in whole 13.89 ms display quanta while the wall clock runs on), so no single constant could cancel it. `pose_lookup_trim_ms` (default 0) is left only for a constant residual: start-vs-middle of exposure. The once-a-second `openxr pdt sync` line is the health check — the stamping is only valid while pdt advances exactly once per `_process`, i.e. `ratio` ≈ 1.00 with `dupes=0`. `use_xr_locate_space` (default ON) picks the locator; a frame the runtime will not answer falls back to the history by itself, counted as `locate_fallbacks` on the flow trace, so neither setting can strand the app. The once-a-second `openxr locate check` lines are the gate and they passed on the Quest: **(A)** locating at `get_predicted_display_time()` reproduces `XRCamera3D` to 0.02–0.3 mm (so the VIEW space and the conversion are right, and Godot's head pose belongs to pdt rather than `get_next_frame_time()` — one display period is worth ~7 mm at normal head speed), **(B)** `pdt − 60 ms` comes back valid and tracked 1–31 mm from the live pose, i.e. this runtime really serves measured history rather than clamping to the newest pose. Both need head *motion* to mean anything. `openxr locate raw` prints the play-space pose before any conversion, which is what distinguishes "wrong pose" from "no pose at all".

**Consuming markers.** The standard route is `XRServer.tracker_added` + `XRAnchor3D`, which is what `main_3d.gd` and `examples/marker_tracking_example.gd` demonstrate. On top of it the node offers an id-keyed API — `get_marker_pose` (PLAY space) / `get_marker_world_pose` (WORLD space) / `has_marker` / `marker_age_ms` / `markers_fresh` / `markers_ever_seen` / `get_average_marker_pose` / `get_marker_size` / `get_marker_tracker` / `get_tracker_name_for`, plus `markers_updated(ids)`. **Watch the space:** the pre-addon script returned WORLD space from `get_marker_pose`, so ported code compiles, runs, and is wrong by the `XROrigin3D` transform. `_sync_marker_sizes` now only refreshes live trackers' `bounds_size` from `processor.get_marker_size(id)`; the id → size table it used to mirror for the C++ side is gone, and its old "only while no task is in flight" contract went with it. `xr_startup.gd` (on the `XROrigin3D`) switches on Meta passthrough (alpha blend + transparent viewport) and the XR viewport — it does **not** initialise OpenXR: `xr/openxr/enabled=true` in `project.godot` means the engine does that before the main scene loads, which is why `_setup_xr_locator`'s `is_initialized()` check does not depend on node order.

**The measurement apparatus attaches by SIGNAL and is not shipped.** The addon exposes three — `detection_applied(image, corners, poses, head_pose)` once per finished detection, `frame_sampled(pdt, now_usec, xr_clock_offset_ns, pdt_stamping, delta)` once per `_process`, `xr_locator_ready(locator, xr_api, to_world)` once — plus `get_processor()` for the two native methods the rig needs (`get_lens_pose`, `project_marker_corners`). Every type in those signatures is an engine or extension class, so the addon stays self-contained; a signal with no listeners costs nothing. Everything the rig needs is HANDED OVER rather than read back, above all `_xr_clock_offset_ns`: the host resamples it, and a second copy on the diagnostics side could diverge from the one the pose lookup uses — precisely the failure the pdt check exists to catch. `_play_space_to_world` travels as a `Callable` for the same reason, which is what keeps check (A) a test of the *time* argument rather than of a second copy of the conversion. `detection_applied` carries the image as an ARGUMENT, which makes "emit before the pending frame overwrites `_detecting_img`" structural rather than a comment about call order.

**`DetectionDiagnostics`** (`project/detection_diagnostics.gd`) holds the hand-eye capture (the `handeye_capture` switch, the motion gate, the JSONL sample file), the per-detection `marker drift` readout with its median-seeded per-id reference, and the OpenXR timing validation (`openxr pdt sync`, `openxr locate check`, `openxr locate raw`). Its `xr_camera`/`xr_origin` are its own scene wiring now — the addon has no scene-tree references to hand over. **`TcpDebugStream`** (`project/tcp_debug_stream.gd`) owns the socket end to end: lifecycle, reconnect, drop accounting, the wire format and the reprojection latch (`REPROJ_BASELINE_MS`), driven by its own `_process` so the host does not tick it. Both resolve the processor LAZILY rather than in `_ready`, because Godot readies CHILDREN BEFORE PARENTS and the host has not built it yet at that point. Removing either facility is deleting a node.

The streamer talks to `tools/tcp_receiver.py` (port 7007 via `adb reverse`), which writes one folder per kind of capture, all stamped `<name>_YYYYMMDD_HHMMSS` at the moment the file is opened and all anchored on the script's own location rather than the shell's cwd: `tools/saved_from_stream/` ('s', the only input set `cameraCalibration.py` globs), `tools/reproj_logs/` ('l', with `plot_reproj_log.py`'s PNGs beside the CSV; both plot scripts share `tools/plotlib.py` — palette, axis styles, NaN-gapping across dropouts, the percentile clipping with its off-scale markers, and the dots-are-samples convention — so the two cannot promise different things about the same kind of panel), `tools/marker_poses/` (the device's `record_global_marker_pos` switch, with `plot_marker_pos.py`'s PNGs one level down in `marker_pose_plots/` since a two-marker recording makes eight of them), and `tools/handeye_samples/` for the JSONL pulled off the headset (`DetectionDiagnostics` stamps that one device-side too, so its name has to be read out of logcat or `run-as … ls files/` before the `adb exec-out` — see the header of `tools/handeye_solve.py`). One packet carries the frame plus **two** overlays and a trailer — the detection's pixel corners (green), the same markers *reprojected* (red), and the baselines — and the receiver draws both with `cv2.aruco.drawDetectedMarkers`, so what you see is what the **device** produced rather than a second opinion from a laptop-side detection. Frame, both marker blocks and the trailer go into the one `_tcp_out` buffer — built with a `StreamPeerBuffer` in big-endian mode rather than by hand — because it drains asynchronously with `put_partial_data`, so anything written to the socket directly would overtake the pixels still queued in front of it, and a dropped frame has to drop its markers with it. The frame opens with its own **`total_size`**, patched in with `seek(0)` once the buffer is complete (rather than computed from the marker counts, which would be a second description of the layout that could disagree with the writer). That length is what makes the format safe to work on: the receiver takes exactly that many bytes off the socket and parses them **in memory**, so a parse failure, an undisplayable format or a version mismatch costs the frame it is in and nothing after it, and `tcp_receiver.py`'s `read_frame()` is the only place that has to be careful. It replaced an invariant maintained by hand — every block consumed for every frame, in order, or the stream desyncs permanently — that four separate comments in the receiver existed to defend. Sender and receiver must still be updated together, but that is now an error message naming both files rather than a session of plausible garbage. (The block the wire format still calls `world` is play space since the merge; identical whenever the `XROrigin3D` sits at identity, which is every setup this has been used in.)

The **red overlay is the lens-pose test**, and it exists because the green one cannot be. Green shows only the ArUco corner extraction: `corners_out` is filled *before* the solve loop and never touches `camera_intrinsics` or `camera_distortion`, so a perfect green fit proves the detector is good and says nothing whatever about the intrinsics or the lens pose. Red is `project_marker_corners(world_poses, head_pose)` (C++, beside the detection so it uses the same `Kamera_matrix`, `distort_mat` and `lens_pose`, and the **native-frame** intrinsics — unscaled by `image_downscale_factor`, since green was already divided back into original-frame pixels): it inverts `head_pose * lens_pose`, undoes the OpenCV→Godot basis change (`F = diag(1,-1,-1)`, its own inverse — the sign pattern looks transposed against the forward path because that builds the `Basis` from *columns* while godot-cpp indexes *rows*), and runs `cv::projectPoints`. It must be fed poses from a DIFFERENT frame: reprojecting a frame's own poses with its own head pose cancels algebraically (`(H·L)⁻¹ · H·L·M = M`) and would draw a perfect square however wrong the lens pose is. So `TcpDebugStream.submit` latches the world poses for `REPROJ_BASELINE_MS` (5000 ms — long enough to cover the same displacement slowly *and* quickly inside one hold, which is what separates a geometry error, scaling with how far the head moved, from a timing error, scaling with how fast) and reprojects *those*. The baseline length is the whole sensitivity of the test: the gap goes as `fx · head_turn · lens_error / range`, so with `fx = 435` and a marker at 0.65 m a 5 mm lens error over the ~80 ms between two detections is **0.3 px** (invisible) while the same error over a second of head turning (~50°) is ~3 px (visible). A longer baseline costs nothing when the calibration is right — a correct world pose is head-independent, so red stays on green however old the reference is; it only bounds how long the marker must stay continuously in view. **The head has to move and the marker must not**: standing still drives the gap to zero regardless of the calibration, which is why the baselines ride along in the trailer — head turn in degrees, plus the displacement as three SIGNED components in the LATCHED HEAD's own frame (x right, y up, z backwards; the receiver derives the L2 norm) — and the receiver prints them first and refuses to interpret a gap until one has grown. The translation keeps its axes because sideways and vertical move the viewpoint ACROSS the marker and so generate the parallax that exposes a wrong depth, while forward/back only changes range. Attribution between those axes is done by a joint least-squares fit in plot_reproj_log.py, never by eyeballing per-axis curves: each curve spans only its own axis's range, so a short axis looks steeper than a long one even when it drives nothing — and the fit reports corr(lateral, forward) beside its slopes, since a sweep that moves in both at once cannot identify the split at all. Which one grew is the diagnosis, and they are not interchangeable. **Turning** exposes `lens_translation`; **strafing cannot**, because with the head orientation fixed the relative motion `A` is a pure translation and `L⁻¹AL = [I | R_Lᵀ·Δ]`, in which `t_L` has cancelled out entirely. What strafing exposes instead is anything that puts the marker at the wrong *depth* — `aruco_patch_sizes` or the focal length — since parallax against a wrongly-placed point grows with viewpoint change, at `fx · (Δ/range) · |1 − 1/k|` for a scale error `k` (0.5% at 0.5 m and 0.65 m ≈ 1.7 px, i.e. right at the visibility threshold). `lens_rotation_raw` shows up under both. So a sawtooth that appears when strafing but not when turning is a scale problem, not a lens-pose one, and reaching for another hand-eye run would be chasing the wrong parameter. The value of all this over judging the rendered mesh through the headset is that it lands in **camera pixels**, with passthrough reprojection onto the depth proxy and the eye projection out of the loop — the two stages that make the naked-eye comparison ambiguous. What it measures is `lens_pose` *and* the capture-time head-pose lookup jointly; a timing error scales with head *velocity* while a lens error scales with head *displacement*, so slow-but-wide head motion isolates the lens pose.

**Camera backends** — Android/Quest uses the `GodotAndroidCamera` Android plugin (`project/addons/GodotAndroidCamera`, a CameraX AAR): frames arrive as raw Y-plane bytes on the CPU (no GPU→CPU readback) together with the **sensor timestamp** of each frame, which is mapped onto Godot's clock to look up the head pose at the true capture time. The offset is calibrated against the clock the feed actually stamps on: boottime (`get_clock_offset_nanos`) for `timestamp_source: "realtime"`, CLOCK_MONOTONIC (`get_monotonic_clock_offset_nanos`) for `"unknown"` — the Quest passthrough feeds report "unknown", and the boottime offset would be silently wrong by the headset's doze time since boot. XrTime (the predicted display time the pose history is stamped with, above) is CLOCK_MONOTONIC on the Quest and therefore gets its own bridge, `_xr_clock_offset_ns`; both are resampled together in `_resample_clock_offsets` so they cannot drift apart — the lookup compares a camera timestamp mapped with one against a history entry mapped with the other, so an error common to both cancels while a divergence becomes a silent bias (on the passthrough feeds they hold the same number). If the plugin singleton or its GDScript wrapper is missing, the addon falls back to Godot's native CameraServer (4.5+) with the fixed `camera_latency_ms` guess. Windows desktop needs the `CameraServerExtension` addon, instantiated via `ClassDB.instantiate()` with an untyped var so the script still parses where that class doesn't exist. Both are bundled into the release zip, because both are optional at RUNTIME and a consumer would therefore never discover they were missing. Rebuilding the AAR: `./gradlew build` in `../godot-android-camera`, then copy `plugin/demo/addons/GodotAndroidCamera` over `project/addons/GodotAndroidCamera`.

**Export guard (`project/addons/opencv_aruco/export_check.gd`, registered by the addon's `plugin.gd`)** — an `EditorExportPlugin` that fails the Android export if a required `.so` is missing for an enabled ABI. Without it Godot packages a 0-byte `.so` and reports success. It also deletes the broken APK in `_export_end()`. Keep its `ABI_ARCHS` map in sync with the `.gdextension` file.

## Platform gotchas (hard-won, do not regress)

- **Android API level is pinned to 24** in `SConstruct` (godot-cpp defaults to 21) because `libcamera2ndk` only exists in the NDK sysroot from API 24+. The Android branch also explicitly links `camera2ndk android log`. The pin's *reason* changed in 2026-08: it used to be OpenCV's videoio backend, but videoio's only callers were the two deleted legacy entry points — what needs Camera2 now is `dump_quest_camera_metadata()`, which calls `ACameraManager_*` directly, and `camera2ndk` appears in no Conan list, so that explicit `-l` is the only thing supplying it. Only a future removal of that dump could lift the pin. `mediandk` came off that line as a duplicate — Conan's opencv `cpp_info` already carries it — but the built `.so` still lists `libmediandk.so` as `DT_NEEDED` while using **zero** symbols from it (measured with `llvm-readelf --dyn-syms`: of 307 undefined symbols exactly 7 are NDK camera symbols, all `ACamera*`, no `AMedia*`/`AImage*`). Dropping it for real means `opencv/*:videoio=False` in `conanfile.py`, which costs a full OpenCV rebuild. CI therefore does NOT assert `libmediandk` in the built `.so` — that would be testing the dependency graph rather than this project; `libcamera2ndk`, which the code genuinely calls, is asserted.
- **C++ exceptions are enabled** (`disable_exceptions=False`) — OpenCV headers require them; godot-cpp disables them by default.
- **Windows CRT matching**: Conan's `compiler.runtime` is derived from godot-cpp's `use_static_cpp` (→ `/MT`). Never link `*d.lib` debug variants of third-party libs — godot-cpp's `template_debug` still uses the release CRT.
- **Quest hand-tracking**: a "controllers required" dialog on launch means the APK lacks the hand-tracking feature — enable Meta Hand Tracking (Optional) in the export preset.
- **Camera feed selection**: Quest exposes feed "1 | FRONT" plus the passthrough pair "50 | BACK"/"51 | BACK"; pick a "BACK" feed, and `CameraServer.monitoring_feeds = true` plus `feed.set_format(...)` must happen before `set_active(true)` or no frames arrive.
- NDK version `23.2.8568313` is pinned by godot-cpp; the Conan profile's `compiler.version=12` matches its clang. OpenXR Vendors plugin v5 lives in `project/addons/godotopenxrvendors`.

Comments in `SConstruct`, `conanfile.py`, and parts of the C++ are in German; that's the existing style, keep edits consistent with the file you're in.

The README documents the full Windows + WSL + Quest workflow in detail (tracks 1–4 plus the native-Windows alternative 5b); point users there rather than re-deriving setup steps.
